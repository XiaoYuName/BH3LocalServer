# 服务端业务接入规范

适用于本工程、工具和测试。先读 [架构](ARCHITECTURE.md)、[状态](STATUS.md)及所属专项；实施顺序见 [WORKFLOW](WORKFLOW.md)。

## 业务所有者

| 领域 | 当前入口 | 接入要求 |
| --- | --- | --- |
| 报文 | `GamePacketCodec`、`HandshakeCodec` | 先检查完整长度、头尾与上限，再解读字段 |
| 可靠传输 | `IReliableChannel` | 确认 BH3 的 KCP 方言后实现；UDP 不能直接送入游戏分帧 |
| 会话 | `GameSession`、`SessionRegistry` | 明确断线、重连、超时和账号绑定边界 |
| 消息 | `IGameMessageHandler`、`GameDispatcher` | 记录消息号依据、所需状态；重复注册报错，未知消息不回成功 |
| 玩家 | `PlayerService` | 用已认证会话 UID；不接受客户端指定其他玩家作为写入目标 |
| 存档 | `IPlayerStore`、`SqlitePlayerStore` | 完整事务或条件更新，提交后才能构造成功响应 |
| 宿主 | `ServerComposition`、`ServerRuntime` | 只装配、监听、停止，不堆业务分支 |

## 协议与规则依据

抓包证明某份报文布局，不证明所有账号、角色、关卡都有相同取值。消息号、protobuf 字段和认证票据必须有当前 9.1 的依据。
旧 Python 的 4/5/6/7 命令号与最小成功包只作为历史线索，没有注册到正式分发器。
9.1 dispatch 密钥已经独立验证，但这不能证明游戏会话加密密钥或 KCP 字段相同。

新增处理器先说明请求/响应、身份、合法状态、失败语义和证据文件，然后编写 codec、用例和注册。
未知字段保留原样；缺少证据的成功响应保持未实现。测试假处理器只能出现在测试工程。

## 事务和恢复

账号创建与玩家档案创建共事务；修订号更新必须携带期望 revision，过期写入不覆盖新数据。
以后涉及道具、货币、奖励和幂等回执时应共事务提交，不能依靠网络重试重复发奖。
数据库已经提交但响应丢失，使用回执/重新读取恢复，不能随意回滚已提交结果。

schema 从 1 开始。已发布迁移只追加，不改写历史；更高版本库和其他应用的数据库明确拒绝。
所有 SQLite 连接通过 `SqliteConnectionFactory` 打开，保证每条连接启用外键。

## 验证要求

修改对应层时运行相应测试；交付前运行 `test.bat` 和发布版隔离验证。
覆盖正常、重复、非法状态、截断、容量、事务失败、竞争写入和重启恢复。
测试用随机端口和临时库，不使用 `dist/server/data/` 的玩家档案。
文档分别记录编译、自动测试、发布进程和真实客户端结果，不能用健康接口通过替代进入大厅验收。
