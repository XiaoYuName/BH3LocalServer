# 战斗准备反复查询编队 · 1.3.5

## 实机现象

用户在 1.3.4 已能进入章节并点击“战斗准备”，随后卡住，尚未进入出战女武神选择。
本次日志共 1119 条游戏请求，全部 Handled；其中 `GetAvatarTeamDataReq`（47）出现 889 次，均收到 48。首次是登录初始化，另外 888 次集中在准备页面打开后的约 7.5 秒。没有 43/45 开战或结算请求。

原始记录保存在 `evidence/lobby/user-client-10.jsonl`、`user-launcher-10.txt`、`user-output-10.txt`。客户端日志没有新的空引用。现有证据指向已响应协议的内容不满足页面条件。

## 9.1 静态依据

| 方法与 RVA | 行为 |
| --- | --- |
| `PlayerModule.OnGetAvatarTeamDataRsp`，`0x68bb4b0` | 清空对应 stage_type 的队员列表，再加入服务端返回的全部 ID |
| `ECCPOOCAPJI.ConvertList`，`0x77026a0` | 逐个复制 ID，保留 0 |
| `LevelPreparePageContext.IsTeamMemberValid`，`0x6507e00` | 逐个解析队员；`0x65080f7` 的空对象分支跳到 `0x6507ff0`，将校验结果置为 false |
| `LevelPreparePageContext.SetupView`，`0x6506300` | 校验失败后创建等待 48 的转圈组件，并再次请求 47；该等待忽略超时 |
| `LevelPreparePageContext.OnGetAvatarTeamDataRsp`，`0x650acd0` | 成功响应再次调用 SetupView；错误成员不变时形成重复请求 |

旧包只拥有角色 101，却返回 `[101, 0, 0]`。这里的 0 会参与角色查询，不表示空白 UI 槽位，因此页面持续等待。旧响应正文为 `080012080801106510001000`（12 字节）。
依据来自本机 9.1 文件的静态分析，哈希与片段记录于 `team-prepare-static-proof.json`、`team-prepare-static/`。没有启动、附加或操作实际游戏。

## 服务端修改

`LobbyHandlers.Create` 的 47/48 处理器直接发送 `CampaignService.Team(uid)`，取消 `Concat([0,0]).Take(3)` 的补零。
修改字段为 `GetAvatarTeamDataRsp.AvatarTeamList[StageType=1].AvatarIdList`：当前账号从 `[101,0,0]` 改为 `[101]`，正文为 `0800120408011065`（8 字节）。

已有 49 `UpdateAvatarTeamNotify` 会过滤输入中的空槽并验证角色归属，仍无独立响应；43/44、45/46 继续处理开战、结算。存档继续使用 schema 3，队伍查询不扣体力。

## 离线验证

- 同一组分层测试在旧代码上因两个 0 无法匹配角色而失败；修改后覆盖默认队伍、保存含空槽的通知、重新创建服务实例、角色归属检查，以及使用返回队伍进入 10101。
- 独立 KCP 消费 24/25 的角色表与 47/48 的编队表，按客户端成员查询规则检查。覆盖 32/64 位帧、重启、重复读取、49 保存通知、非法角色更新，以及零 ID/未知角色反例。
- 旧 1.3.4 的 15 项观察：12 项编队就绪检查失败，3 项反例判定通过。新版结果见本页“最终结果”和四角色验证记录。

此重放验证普通自有角色的成员存在性条件，不等同于运行 UI；试用角色过期、其他玩法与实际战斗仍需后续证据。
